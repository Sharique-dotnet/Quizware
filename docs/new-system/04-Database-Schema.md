# 4. Detailed Database Schema

**Target:** Microsoft SQL Server (2019 or later, or Azure SQL)
**ORM:** EF Core 10, code-first migrations
**Style:** singular table names, `PascalCase`, `Id` primary keys

---

## 4.1 Conventions used everywhere

### Primary keys

`UNIQUEIDENTIFIER` with `DEFAULT NEWSEQUENTIALID()`.

Why GUIDs instead of `INT IDENTITY`:
- Ids can be generated by the client, which makes idempotent retries easy
- No id collisions if data is ever merged from another program or environment
- `NEWSEQUENTIALID()` keeps the clustered index from fragmenting

Small fixed lookup tables use `TINYINT` / `SMALLINT` codes instead.

### Audit columns (on every business table)

| Column | Type | Meaning |
|---|---|---|
| `CreatedAtUtc` | `DATETIME2(3) NOT NULL` | When the row was created |
| `CreatedBy` | `UNIQUEIDENTIFIER NULL` | User who created it |
| `UpdatedAtUtc` | `DATETIME2(3) NULL` | Last change |
| `UpdatedBy` | `UNIQUEIDENTIFIER NULL` | Who changed it |
| `IsDeleted` | `BIT NOT NULL DEFAULT 0` | Soft delete |
| `DeletedAtUtc` | `DATETIME2(3) NULL` | When soft-deleted |
| `DeletedBy` | `UNIQUEIDENTIFIER NULL` | Who soft-deleted it |
| `RowVersion` | `ROWVERSION` | Optimistic concurrency |

These are set automatically in `SaveChangesAsync`, never by hand.

### Tenant column

Every program-owned table has:

```sql
ProgramId UNIQUEIDENTIFIER NOT NULL
    CONSTRAINT FK_<Table>_Program FOREIGN KEY REFERENCES Program(Id)
```

and an EF Core global query filter that adds
`WHERE ProgramId = @currentProgram AND IsDeleted = 0` to every query.

### Text and time

- All text is `NVARCHAR` (the content is Urdu).
- All times are UTC, stored as `DATETIME2(3)`, and column names end in `Utc`.
- Money-like values are not used; points are `INT` and may be negative.

### `ProgramQuestionFormat` — which question types this program uses

**No question format is compulsory.** This table lets an organiser declare, in
one place, which of the ten formats their event actually uses.

| Column | Type | Notes |
|---|---|---|
| `Id` | `UNIQUEIDENTIFIER` PK | |
| `ProgramId` | FK → `Program` NOT NULL | |
| `FormatId` | `TINYINT` FK → `QuestionFormat` NOT NULL | |
| `IsEnabled` | `BIT` NOT NULL DEFAULT 1 | Turn a format off for this program |
| `DisplayOrder` | `INT` NOT NULL DEFAULT 0 | Order in admin dropdowns |
| `DisabledReason` | `NVARCHAR(300)` NULL | "No buzzer hardware this year" |
| *(audit)* | | |

**Unique:** `UX_PQF (ProgramId, FormatId) WHERE IsDeleted = 0`.
**Index:** `IX_PQF_ProgramId_IsEnabled`.

**Purpose.** Disabling a format here removes it from every admin dropdown, the
question-bank filters, the import templates and the segment-template picker. It
is a **convenience and a safety net**, not the mechanism that decides what is
played — that is `StageSegmentTemplate`.

**What disabling does and does not do:**

| Does | Does not |
|---|---|
| Hide the format from admin screens | Delete any existing questions |
| Block new segment templates using it | Alter matches already created |
| Exclude it from the coverage report | Affect other programs |
| Exclude it from readiness validation | Affect the shared question library |

Rows are created automatically when a program is created, all enabled by
default, so an organiser who ignores this table entirely gets today's behaviour.

**Constraint:** a format cannot be disabled while a `StageSegmentTemplate` in
that program still references it — the API returns
`FORMAT_IN_USE` naming the stages that use it, so the disable is never silently
destructive.

## 4.7 Question bank tables

### The design decision: Table-Per-Type (TPT)

Different formats genuinely need different fields. A Sequence question needs a
correct position per item; an Audio-Visual question needs a media file, a
playback window and a spoken answer; a Passing question needs a maximum pass
count. Forcing all of that into one wide table would mean a lot of columns that
are `NULL` for most rows, and no database-level guarantee that the right ones are
filled in.

So **each format gets its own table**.

At the same time, all ten formats share the same *identity and lifecycle*:
they belong to a program, have a difficulty, a topic, a language, an approval
status and a usage count. Copying those 15 columns into ten tables is exactly
what produced the 75–80% duplication in the current system.

**The design therefore splits the two concerns:**

```
                      ┌──────────────────────────────┐
                      │          Question            │   BASE TABLE
                      │  Id, ProgramId, FormatId,    │   what every format shares:
                      │  QuestionText, Difficulty,   │   identity, classification,
                      │  Topic, Language, Status,    │   lifecycle, usage stats
                      │  TimesUsed, audit...         │
                      └──────────────┬───────────────┘
                                     │ shared primary key (1:1)
   ┌──────────┬──────────┬───────────┼───────────┬──────────┬───────────────┐
   ▼          ▼          ▼           ▼           ▼          ▼               ▼
┌──────┐ ┌────────┐ ┌─────────┐ ┌──────┐ ┌────────┐ ┌──────────┐ ┌────────────────┐
│ Mcq  │ │ Buzzer │ │ Passing │ │ Card │ │ Choice │ │ Sequence │ │  AudioVisual   │
│Quest.│ │ Quest. │ │  Quest. │ │Quest.│ │ Quest. │ │  Quest.  │ │    Question    │
└──┬───┘ └───┬────┘ └────┬────┘ └──┬───┘ └───┬────┘ └────┬─────┘ └───────┬────────┘
   │         │           │         │         │           │               │
   └─────────┴───────────┴─────────┴─────────┘           │               │
                         │                               │               │
                         ▼                               ▼               ▼
                 ┌───────────────┐              ┌───────────────┐  (MediaAsset)
                 │ QuestionOption│              │ SequenceItem  │
                 └───────────────┘              └───────────────┘

   ┌───────────────┐ ┌─────────────────────┐ ┌──────────────────┐
   │ RapidFire     │ │ VisualRapidFire     │ │ TieBreaker       │
   │ Question      │ │ Question ──► Items  │ │ Question         │
   └───────────────┘ └─────────────────────┘ └──────────────────┘
```

**What you get:** ten real tables, each with only the columns its format actually
needs, each independently constrainable — plus one shared table so the common
columns exist once instead of ten times.

**Everything else in the system references `Question.Id`** — `MatchQuestion`,
`QuestionUsageHistory`, `QuestionSelectionRule`, `AnswerRecord`. None of them
need to know which format table is involved. This is the property that keeps the
match engine a single engine.

CREATE NONCLUSTERED INDEX IX_Question_Selection

ALTER TABLE Question ADD CONSTRAINT CK_Question_OwnerScope

### The ten format tables

Every one uses the same pattern:

```sql
QuestionId UNIQUEIDENTIFIER NOT NULL
    CONSTRAINT PK_<Format>Question PRIMARY KEY,
    CONSTRAINT FK_<Format>Question_Question
        FOREIGN KEY REFERENCES Question(Id) ON DELETE CASCADE
```

`QuestionId` is **both the primary key and the foreign key** — a shared primary
key, so the relationship is strictly one-to-one and no extra id is needed.

| `NegativeMarkingEnabled` | `BIT` NOT NULL DEFAULT 0 | |

### EF Core mapping

EF Core supports this natively with the TPT strategy — no manual joins:

```csharp
// Domain: an abstract base with one class per format
public abstract class Question           { /* shared columns */ }
public sealed class McqQuestion             : Question { public bool AllowMultipleCorrect { get; set; } /*...*/ }
public sealed class BuzzerQuestion          : Question { public int  BuzzWindowSeconds    { get; set; } /*...*/ }
public sealed class AudioVisualQuestion     : Question { public Guid MediaAssetId         { get; set; } /*...*/ }
public sealed class SequenceQuestion        : Question { public int  SequenceLength       { get; set; } /*...*/ }
// ... and the other six

// Configuration
modelBuilder.Entity<Question>()
    .UseTptMappingStrategy()                     // one table per type
    .ToTable("Question")
    .HasDiscriminator(q => q.FormatId);          // kept as a real, queryable column

modelBuilder.Entity<McqQuestion>().ToTable("McqQuestion");
modelBuilder.Entity<BuzzerQuestion>().ToTable("BuzzerQuestion");
modelBuilder.Entity<AudioVisualQuestion>().ToTable("AudioVisualQuestion");
// ...
```

Querying is then natural:

```csharp
// Selection — touches ONLY the base table. No joins, no format knowledge.
var pool = await db.Questions
    .Where(q => q.FormatId == formatId
             && q.DifficultyLevelId >= min && q.DifficultyLevelId <= max
             && q.Status == QuestionStatus.Approved)
    .Select(q => new { q.Id, q.TopicId, q.TimesUsed })
    .ToListAsync(ct);

// Loading one drawn question — EF joins the right format table automatically
var question = await db.Questions
    .Include(q => q.Options)
    .FirstAsync(q => q.Id == id, ct);

// Format-specific work, strongly typed
if (question is AudioVisualQuestion av)
    await mediaService.PrepareAsync(av.MediaAssetId, av.PlaybackStartSeconds, ct);
```

**If you would rather not use EF inheritance at all,** the same tables work as
plain one-to-one relations: keep `Question` as a normal entity and give each
format entity a `QuestionId` primary key with a required reference back. The SQL
schema is identical; only the C# mapping style changes.

---

### Why `AnswerRecord` stays a single table

The nine `*_Answers` tables in the current system are still merged into one.
That is a different situation from questions:

| | Questions | Answers |
|---|---|---|
| Field variance between formats | **Real** — media, sequence order, pass count, topic | **None** — every answer is (team, question, outcome, points, when, who) |
| What the old tables differed in | Genuinely different columns | Only the FK column name |
| Result | Ten tables, justified | One table, justified |

The small variance that does exist — a selected option, a submitted order, free
text — is covered by three nullable columns on `AnswerRecord`, and the format is
always reachable through `MatchQuestion → Question.FormatId`. Splitting answers
would fragment the scoring ledger and force the match engine to branch by format
on every write, which is exactly the duplication being removed.

---

### Trade-offs of this design, stated honestly

| Aspect | Effect |
|---|---|
| Field correctness | **Better.** `AudioVisualQuestion.MediaAssetId` can be `NOT NULL`; in a shared table it would have to be nullable. |
| Clarity | **Better.** The schema documents each format instead of hiding it in nullable columns. |
| Duplication | **Controlled.** The 15 shared columns exist once, not ten times. |
| Reading one question | **One extra join.** Negligible — a single-row lookup on a shared primary key. |
| Question selection | **Unaffected.** The draw touches only the base table and its one index, so the hottest query gets no slower. |
| Adding a new format | **One small migration** (a new table) instead of zero. This is the real cost of the decision — accepted, because formats are added roughly once a year. |
| Bulk question list screens | Query the base table; join a format table only when the user filters to one format. |
| Referencing questions elsewhere | **Unaffected.** `MatchQuestion`, `AnswerRecord` and the rules all point at `Question.Id`. |

**Purpose:** this single table encodes what today is spread across three

**Changing the order of question types** is now an update to `OrderIndex` on
these rows — one `PUT` from a drag-and-drop list, no deployment. Compare with the
current system, where the order lives as a hardcoded `window.location.href` in
each of 108 views (finding 1.4g).

**Which question types are played is decided entirely by which rows exist here.**
No format is compulsory. To drop Passing from a year's event, simply do not
create a Passing row — nothing else in the system needs to change, and no
Passing questions need to be authored. A stage with four segment rows plays four
segments.

**Three different meanings of "optional" — worth keeping straight:**

| Meaning | How | Effect |
|---|---|---|
| **Not used at all this year** | No `StageSegmentTemplate` row exists | The format never appears. No questions needed, no rules needed. **This is the common case.** |
| **Planned, but skippable on the night** | A row exists with `IsOptional = 1` | Questions are drawn and reserved; the operator may skip the segment with a recorded reason |
| **Switched off program-wide** | `ProgramQuestionFormat.IsEnabled = 0` | Hidden from every admin screen so it cannot be picked by accident |

The first is the one you want when you say "this year we are not doing
Passing".

Three levels of control, most specific winning:

| Level | Where | Effect |
|---|---|---|
| Stage default | `StageSegmentTemplate.OrderIndex` | Applies to every match in the stage |
| Per match | `MatchSegment.OrderIndex` | Copied from the template at match creation, then editable — so Semi-Final Match 1 can differ from Match 2 |
| Live | `MatchSegment.OrderIndex` on *pending* segments | Only when `Stage.AllowSegmentReorderDuringMatch = 1` |

Because `MatchSegment` already carries its own `OrderIndex`, a per-match order
costs no extra table — the match simply keeps the order it was given.

| *(audit)* | | |

**Unique:**
- `UX_MP_Match_Team (MatchId, TeamId) WHERE IsDeleted = 0`
- `UX_MP_Match_Seat (MatchId, SeatNumber) WHERE IsDeleted = 0`

**Index:** `IX_MP_MatchId_StatusId_TurnOrder` — this is the hot query.

**Purpose and how it solves your problem:**

Today, turn order is `QuestionNumber % 3` — a number baked into code. Here, turn
order is a **column**. When a team is disqualified:

```sql
UPDATE MatchParticipant
   SET StatusId = 2, RemovalReason = @reason, RemovedAtUtc = SYSUTCDATETIME()
 WHERE MatchId = @m AND TeamId = @t;

-- recompact turn order over the remaining active teams
WITH ranked AS (
  SELECT Id, ROW_NUMBER() OVER (ORDER BY TurnOrder) AS NewOrder
    FROM MatchParticipant
   WHERE MatchId = @m AND StatusId = 1 AND IsDeleted = 0)
UPDATE mp SET TurnOrder = r.NewOrder
  FROM MatchParticipant mp JOIN ranked r ON r.Id = mp.Id;
```

The engine then simply does
`activeParticipants[questionIndex % activeParticipants.Count]`.
The match carries on with 2 teams. No fake answers, ever.

**Result: 32 tables become 51.**

The question area keeps a table per format — 10 format tables, as you asked — but
their 15 shared columns now live once in the `Question` base table instead of
being copied ten times. The six identical `*_Option` tables collapse into one,
while `Sequence` and `VisualRapidFire` keep their own child tables because their
items genuinely differ in shape. The nine `*_Answers` tables become one, because
answers really are uniform.

The remaining new tables add security, audit, recovery and configurability that
simply did not exist — including the three `TieBreak*` tables, which turn "the
tie was settled by whichever row the database returned first" into a configurable
rule, a real played match, and a permanent record of the decision.

## 4.14 Key indexes for the hot paths

```sql
-- 1. Question selection at match start (the most performance-critical query).
--    Hits the BASE table only — no format table is touched during the draw,
--    so splitting questions per format costs this query nothing.
CREATE NONCLUSTERED INDEX IX_Question_Selection
    ON Question (ProgramId, FormatId, DifficultyLevelId, Status, IsDeleted)
    INCLUDE (TopicId, Language, TimesUsed);

-- 1b. Format tables need no extra index: their PK IS the FK to Question(Id),
--     so EF's join to load a drawn question is a clustered-index seek.

-- 2. "Which team answers next?" — runs on every question
CREATE NONCLUSTERED INDEX IX_MP_Active_Turn
    ON MatchParticipant (MatchId, StatusId, TurnOrder)
    INCLUDE (TeamId, SeatNumber) WHERE IsDeleted = 0;

-- 3. Live match state fetch
CREATE NONCLUSTERED INDEX IX_MQ_Match_State
    ON MatchQuestion (MatchId, State, OrderIndex)
    INCLUDE (QuestionId, TargetTeamId, MatchSegmentId);

-- 4. Live scoreboard
CREATE NONCLUSTERED INDEX IX_TMS_Match_Points
    ON TeamMatchScore (MatchId, TotalPoints DESC) INCLUDE (TeamId, Rank);

-- 5. Stage leaderboard / "best remaining" qualification
CREATE NONCLUSTERED INDEX IX_TSS_Stage_Points
    ON TeamStageScore (StageId, TotalPoints DESC) INCLUDE (TeamId, Rank);

-- 6. Repeat prevention
CREATE NONCLUSTERED INDEX IX_QUH_Program_Question
    ON QuestionUsageHistory (ProgramId, QuestionId) INCLUDE (TeamId, MatchId);

-- 7. Score recalculation / audit
CREATE NONCLUSTERED INDEX IX_ScoreEvent_Match_Team
    ON ScoreEvent (MatchId, TeamId) INCLUDE (Points, IsReversed, EventType);
```

## 4.15 Important constraints

```sql
-- A team may appear only once in a match
ALTER TABLE MatchParticipant
  ADD CONSTRAINT UX_MP_Match_Team UNIQUE (MatchId, TeamId);

-- Seats are unique within a match
ALTER TABLE MatchParticipant
  ADD CONSTRAINT UX_MP_Match_Seat UNIQUE (MatchId, SeatNumber);

-- A question cannot be served twice in one match
ALTER TABLE MatchQuestion
  ADD CONSTRAINT UX_MQ_Match_Question UNIQUE (MatchId, QuestionId);

-- Stage order is unique within a program
ALTER TABLE Stage
  ADD CONSTRAINT UX_Stage_Program_Order UNIQUE (ProgramId, OrderIndex);

-- Match number is unique within a stage
ALTER TABLE Match
  ADD CONSTRAINT UX_Match_Stage_Number UNIQUE (StageId, MatchNumber);

-- Difficulty must be 1..5
ALTER TABLE Question
  ADD CONSTRAINT CK_Question_Difficulty CHECK (DifficultyLevelId BETWEEN 1 AND 5);

-- A shared-library question has no ProgramId; a program question must have one
ALTER TABLE Question
  ADD CONSTRAINT CK_Question_OwnerScope
  CHECK ((OwnerScope = 1 AND ProgramId IS NOT NULL)
      OR (OwnerScope = 2 AND ProgramId IS NULL));

-- A manual score adjustment must carry a reason
ALTER TABLE ScoreEvent
  ADD CONSTRAINT CK_ScoreEvent_ManualReason
  CHECK (EventType <> 2 OR (Reason IS NOT NULL AND LEN(Reason) > 0));

-- A removed participant must have a reason and a timestamp
ALTER TABLE MatchParticipant
  ADD CONSTRAINT CK_MP_Removal
  CHECK (StatusId = 1 OR (RemovalReason IS NOT NULL AND RemovedAtUtc IS NOT NULL));

-- Stage team-count range must make sense
ALTER TABLE Stage
  ADD CONSTRAINT CK_Stage_TeamRange
  CHECK (MinTeamsPerMatch >= 2 AND MaxTeamsPerMatch >= MinTeamsPerMatch);

-- Sequence positions must be unique within a question
ALTER TABLE SequenceItem
  ADD CONSTRAINT UX_SequenceItem_Position UNIQUE (QuestionId, CorrectPosition);

-- A stage must have at least one segment before it can start.
-- (Enforced in the application: a CHECK constraint cannot count child rows.)

-- A format cannot be disabled for a program while a segment template uses it
-- (enforced in the application; the API returns FORMAT_IN_USE with the stages)

-- Segment order is unique within a stage template and within a match
ALTER TABLE StageSegmentTemplate
  ADD CONSTRAINT UX_SST_Stage_Order UNIQUE (StageId, OrderIndex);
ALTER TABLE MatchSegment
  ADD CONSTRAINT UX_MatchSegment_Order UNIQUE (MatchId, OrderIndex);

-- A tie-break match must point at the tie it resolves, and vice versa
ALTER TABLE Match
  ADD CONSTRAINT CK_Match_TieBreak
  CHECK ((MatchKind = 1 AND TieBreakEventId IS NULL)
      OR (MatchKind = 2 AND TieBreakEventId IS NOT NULL));

-- A tie-break needs at least two tied teams
ALTER TABLE TieBreakEvent
  ADD CONSTRAINT CK_TieBreakEvent_Slots CHECK (ContestedSlots >= 1);

-- A resolved tie must say how it was resolved
ALTER TABLE TieBreakEvent
  ADD CONSTRAINT CK_TieBreakEvent_Resolution
  CHECK (State <> 4 OR (ResolutionMethod IS NOT NULL AND ResolvedAtUtc IS NOT NULL));

-- A manual tie resolution must carry a reason
ALTER TABLE TieBreakEvent
  ADD CONSTRAINT CK_TieBreakEvent_ManualReason
  CHECK (ResolutionMethod <> 3 OR (Notes IS NOT NULL AND LEN(Notes) > 0));

-- Tie-break difficulty range must make sense
ALTER TABLE TieBreakRule
  ADD CONSTRAINT CK_TieBreakRule_Difficulty
  CHECK (MinDifficultyLevelId BETWEEN 1 AND 5
     AND MaxDifficultyLevelId BETWEEN 1 AND 5
     AND MaxDifficultyLevelId >= MinDifficultyLevelId);

-- Partial credit needs a points value
ALTER TABLE SequenceQuestion
  ADD CONSTRAINT CK_SeqQ_PartialCredit
  CHECK (PartialCreditEnabled = 0 OR PointsPerCorrectPosition IS NOT NULL);

-- A steal window is only meaningful when stealing is allowed
ALTER TABLE BuzzerQuestion
  ADD CONSTRAINT CK_BuzzQ_Steal
  CHECK (AllowStealAfterWrong = 1 OR StealWindowSeconds IS NULL);

-- A tie-breaker's answer must match its answer mode
ALTER TABLE TieBreakerQuestion
  ADD CONSTRAINT CK_TieQ_AnswerMode
  CHECK ((AnswerMode = 1)
      OR (AnswerMode = 2 AND AnswerText   IS NOT NULL)
      OR (AnswerMode = 3 AND NumericAnswer IS NOT NULL));
```

**Guarantees the format tables now give you** — none of which a single shared
question table could express:

| Guarantee | Enforced by |
|---|---|
| An Audio-Visual question always has a media file | `AudioVisualQuestion.MediaAssetId NOT NULL` |
| An Audio-Visual question always has an answer | `AudioVisualQuestion.AnswerText NOT NULL` |
| Every Visual Rapid Fire image has its own answer | `VisualRapidFireItem.AnswerText NOT NULL` |
| A Choice question always has a topic label | `ChoiceQuestion.TopicLabel NOT NULL` |
| Sequence positions are unique and gap-free | `UX_SequenceItem_Position` + application check |
| A Passing question always has a pass limit | `PassingQuestion.MaxPassCount NOT NULL DEFAULT 2` |

In a single wide table every one of these columns would have to be nullable,
and the rules could only be checked in C#.

**Option-count rules** (2–8 options, exactly one correct) apply only to the six
option-based formats. They are enforced in the application layer, because a
`CHECK` constraint cannot count child rows. `AudioVisualQuestion`,
`RapidFireQuestion` and `VisualRapidFireQuestion` simply have no options — with
separate tables, that is now obvious from the schema rather than a convention.

**Delete behaviour:** foreign keys use `ON DELETE NO ACTION`, except the format
tables and their child tables, which cascade from `Question` (they are parts of
the same object, not independent records). Nothing is ever hard-deleted;
`IsDeleted` on the base table is the only delete, and the global query filter
hides the whole object. This prevents the accidental cascade wipe that
`spReset`'s `TRUNCATE` performs today.

## 4.16 The multi-program strategy, in one place

| Aspect | Decision |
|---|---|
| Isolation model | One database, shared schema, `ProgramId` column |
| Enforcement | EF Core global query filter, applied to every tenant entity |
| Source of the current program | JWT claim, never a request parameter |
| Uniqueness | Every unique index includes `ProgramId` |
| Shared data | Question bank, topics and tags may be organisation-scoped (`ProgramId = NULL`) |
| Cross-program reporting | A `SuperAdmin` may query across programs through explicit endpoints |
| New event setup | `POST /programs` + `POST /programs/{id}/clone-from/{sourceId}` — no deployment |
| Data volume | With ~50 programs and ~100k questions this stays comfortably small for SQL Server |
| Archiving | Set state to `Archived`; optionally move to an archive filegroup later |
